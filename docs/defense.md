# Подготовка к защите лабораторной работы

Программа решает NER-задачу: каждому токену соответствует один атрибут персональных данных либо `O`. Для восьми атрибутов используются 17 BIO-меток. `B` начинает сущность, `I` продолжает её. Компоненты ФИО разделены на имя, фамилию и отчество. Номер с пробелами может включать несколько токенов, но возвращается как одна сущность с точными позициями.

## Выбор методов

ФИО зависит от контекста, порядка слов, падежа и неоднозначности слова. Дообученный RuBERT использует окружающий текст для выбора класса. Предобучение даёт языковые представления, а дообучение учит нужной разметке. Модель базового RuBERT сама по себе не является готовым распознавателем наших ПДн.

В v2 к модели добавлено уточнение по явным подписям полей. Оно меняет тип/границы уже найденного компонента ФИО, но не заменяет модель словарём. Полный валидный e-mail защищён от вложенных цифровых сущностей до разрешения остальных пересечений. V3 исключает явное животное «Лев» и имена в названиях объектов; частичную составную фамилию расширяет при подтверждении контекстом человека. Полная семантическая неоднозначность омонимов остаётся. Методика и ограничения описаны в [порядке проверки](testing.md).

У номеров и адресов есть структура, поэтому регулярные выражения дают подходящих кандидатов без необходимости учить модель всем цифровым форматам. Контрольные цифры дополнительно отсеивают ошибки. Регулярное выражение отвечает за форму, валидатор — за контрольную сумму. Валидность суммы не означает, что номер был выдан реальному человеку. У e-mail и телефона такой контрольной цифры нет.

Каждое правило возвращает позиции исходного текста. Изменять строку перед определением позиций опасно: пробелы, переносы строк или удалённые символы сместят индексы. Проверяется `text[start:end]`; конец не входит в найденную строку. Это позволяет следующей лабораторной обезличивать фрагменты.

## Метрики

Для каждого класса TP — верно распознанные элементы этого класса, FP — лишние распознавания, FN — пропуски.

`Precision = TP / (TP + FP)` — сколько из найденного оказалось правильным.

`Recall = TP / (TP + FN)` — какую долю эталонных данных удалось найти.

`F1 = 2 × Precision × Recall / (Precision + Recall) = 2TP / (2TP + FP + FN)`.

`Weighted F1 = Σ(support_c × F1_c) / Σ support_c`, где support — число эталонных элементов класса. Это среднее классовых F1, а не F1 от усреднённых precision и recall. При нулевых знаменателях в проекте используется 0.

Основной расчёт выполнен по BIO-токенам ПДн, без `O` в средней. Все токены остаются в сравнении, чтобы ложные срабатывания на обычных словах были ошибками. Вариант с `O` выводится дополнительно: большое число обычных слов может улучшать общую оценку при слабом обнаружении ПДн.

Строгая оценка целых сущностей требует правильных типа и двух границ. Например, распознана только часть телефона — это FP для предсказанного фрагмента и FN для полного эталонного номера. Токенная оценка может зачислить правильно найденные части. Поэтому обе оценки нужны, чтобы объяснить качество границ.

## Разделение данных

Train используется для градиентного обучения. Validation используется для выбора лучшей эпохи и настройки. Test используется только для итоговой оценки. Выбор эпохи по test означает утечку и делает итоговую оценку ненадёжной. В проекте обучение читает только train и validation, проверяются хеши файлов. В исходном наборе семейства синтетических шаблонов разделены между выборками, корпус разделён по документам. В расширении v2 общие семейства форматов повторяются, но новые конкретные тексты не совпадают между train/validation/контрольным набором и исходными тестами. Поэтому отложенные 1000 текстов подтверждают перенос на новые экземпляры этих форматов, а не на полностью новые предметные области.

Первый стресс-набор использовался для диагностики и исправлений, поэтому при повторной оценке он является регрессионным. Контрольный набор из 1000 текстов подготовлен до дообучения и не использовался для выбора эпохи. Его результаты уже изучены; дальнейшая настройка по его ошибкам потребует нового контрольного набора для независимого подтверждения.

Структурированные эталоны создаются из заранее выбранных значений с известными позициями, а не из вывода правил. Иначе проверялось бы совпадение распознавателя с самим собой. При этом генератор и валидаторы используют общую арифметику, поэтому отдельно нужны известные контрольные примеры и отрицательные тесты. Качество на этих синтетических данных не доказывает перенос на произвольные документы.

## Причины ошибок

- Редкое имя, другая предметная область или мало примеров отчества в естественном корпусе.
- Слово одновременно является именем и обычным словом; нужен контекст.
- Необычные падежи, регистр, инициалы, дефисы и опечатки.
- Слишком узкий формат регулярного выражения либо слишком широкий кандидат.
- Совпадение нескольких цифровых форматов, например телефона и СНИЛС.
- Ошибка границы сущности или разметки исходного корпуса.
- Несогласованность слов и подслов BERT, потерянный хвост длинного текста.
- Хорошая средняя при плохом отдельном классе из-за дисбаланса частот.

Для разбора смотрите таблицу по атрибутам, метрики по источникам и примеры FN/FP в отчёте. Улучшения проверяйте на validation; исходный test сохраняйте для окончательной проверки.
